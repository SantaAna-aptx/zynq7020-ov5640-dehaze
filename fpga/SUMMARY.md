# Zynq-7020 上的纯 PL 暗通道去雾 —— 项目总结

**一句话**：在一块 Zynq-7020（米兰科 MZ7X）的 PL 里实现完整的暗通道先验去雾流水线，
含引导滤波细化，1025×720 单帧 **226 ms（无细化）/ 362 ms（含引导滤波）**，
输出与 PC 端浮点参考 **PSNR 49.1 dB**、与 C 仿真 **逐字节相同**；
再往前接上一整套自研的 OV5640 采集通路（SCCB + DVP + 双时钟行缓冲 + AXI 突发写 DDR），
640×480 摄像头进、去雾、出图，整条链路只占 **341 个 LUT**。

---

## 1. 为什么是"纯 PL"

最初想把去雾挂到已有的 YOLO 工程（DPU + OV5640）上，但那个设计已经吃满器件：

| 资源 | DPU 工程 | 本设计 |
|---|---|---|
| Slice | 98.2%（只剩 243 个） | 37.9% |
| DSP | 96.4% | 33% |
| BRAM | 88.2% | 52.5% |

物理上没有余量再塞一条图像流水线。于是拿掉 DPU，只保留最干净的
"图进 → PL 处理 → 图出"骨架，把问题限定在算法与硬件的映射上。

---

## 2. 架构

### 2.1 四趟扫描

```
src ──pass1──> 暗通道(可分离 15×15 min) + 256-bin 直方图 ──> 大气光 A
    ──pass2a─> min_c(I_c/A_c) ──> 透射率 t ──> scratch(t 图)
    ──pass2b─> box(g), box(t) ──> a, b ──> scratch((a,b) 图)      [仅 mode 1]
    ──pass2c─> box(a), box(b) ──> t_ref, 复原 ──> dst              [仅 mode 1]
```

`mode` 寄存器切换两条路径，共用一个比特流：

- **mode 0**：暗通道 + 透射率 + 复原（无细化，边缘有块状伪影）
- **mode 1**：再加 He 的引导滤波细化（r=30，61×61 窗，eps=1e-4）

### 2.2 三个关键设计

**① 大气光用直方图法，不用全排序**

论文取暗通道最亮的前 0.1% 像素。硬件里做全排序不可行，改成：
每个暗通道值 bin 记录「该 bin 内 R+G+B 的最大值及其像素下标」，扫完全图后
从 255 往下累加到 0.1% 得到阈值 T，再在 `v ≥ T` 的 bin 里取最大者。
一遍出结果，只需 256×3 个寄存器级存储。

**② 最小值滤波可分离 + 16 行环形缓冲**

先横向 15 抽头、再纵向 15 抽头，O(1)/像素。缓冲用 16 深（2 的幂）以便
用 `& 15` 掩码代替 15 取模。边界用「行号钳位 + 循环多看 7 行」复刻
`BORDER_REPLICATE`。

**③ 没有运行时除法**

- `1/A`：每帧算一次（3 个除法）
- `1/t`：257 项 ROM（t 只取 0..256 的整数值，查表精确）
- `1/(var+eps)`：归一化倒数 ROM，8 位尾数，相对误差 <0.4%

引导滤波的 `a = cov/(var+eps)` 是唯一的逐像素除法，用
「前导零计数 → 8 位尾数查表 → 移位」实现，零 DSP、II=1。

### 2.3 定点约定

| 量 | 格式 |
|---|---|
| 图像 I、A、guide、p | 8 bit，0..255 |
| 均值、方差、a | Q8（值×256） |
| b | 8 bit 域的普通值（10 bit 有符号存储） |
| 透射率 t | Q8，钳到 [t0, 255] |

复原的核心一步：

```
J = (I - A) × (65536 / t_q8) >> 8 + A
```

注意是 `>> 8` 不是 `>> 16` —— `t_q8` 本身已是 Q8，这一位算错会让所有像素
被拉向大气光，PSNR 掉到 3 dB。

## 3. 结果

### 3.1 正确性

| 判据 | mode 0 | mode 1 |
|---|---|---|
| 大气光 A (B,G,R) | 217,215,214 | 217,215,214 |
| 稀疏校验和（板端打印） | `0x7D194413` | `0xECB8A61A` |
| 与 PC 端 C 仿真逐字节对比 | **完全相同** | **完全相同** |
| 与 Python 浮点参考 PSNR | **49.13 dB** | **49.07 dB** |
| 最大单像素偏差 | 5 | 3 |

### 3.2 性能

| 版本 | mode 0 | mode 1 | 关键改动 |
|---|---|---|---|
| v0 | 593 ms | — | 无引导滤波 |
| v1 | 845 ms | 1397 ms | 加引导滤波 |
| v2 @ div20 | 423 ms | 692 ms | scratch 独立 AXI 主口；边界拆出热循环 |
| v2 @ div8 | 226.7 ms | 362.3 ms | 修正 FCLK0 |
| **v3 @ div6** | **199.3 ms** | **299.2 ms** | 减少 DDR 流量（**实测无收益**）+ 收敛到稳定的最高时钟 |

相对 v1 总计 **4.2× / 4.7×**。最慢的 mode 1（299 ms）也比最初的 v0 mode 0（593 ms）快一倍。

优化过程中的两个主要发现：

**① 把 scratch 挂在 `src` 同一条 AXI 主口上，代价是 42%**
多一个地址寄存器就足以破坏读突发。拆到独立主口（HP2）后立即减半。

**② FCLK0 一直设低了 4 倍**
项目沿用 `devmem 0xF8000170 32 0x00201400` 并注释为"精确 50.000 MHz"。
实测：设计在 divisor 4 下仍逐位正确、在 divisor 3 下出错，与 Vivado 报的
Fmax ≈ 57.8 MHz 吻合 —— 反推 baseline 只有 **~12–14 MHz**。
改到 divisor 8 又白拿 1.87×。

### 3.3 资源

| 指标 | v0 | v2 | **v4（含摄像头）** |
|---|---|---|---|
| Slice LUTs | 6,540 (12.3%) | 14,647 (27.5%) | **14,074 (26.45%)** |
| Block RAM Tile | 20 (14.3%) | ~74 (53%) | **91 (65.0%)** |
| DSP | 16 (7.3%) | 73 (33%) | **63 (28.6%)** |
| WNS @ 50 MHz | +3.957 ns | +2.703 ns | **+3.367 ns** |
| WHS | — | — | +0.043 ns（HLS 域内，非摄像头引入） |

摄像头子系统本身（`cam_top_0`，含 SCCB、采集、行缓冲、DDR 写入、AXI-Lite 状态口）
只占 **373 LUT / 593 FF / 2×RAMB36 + 1×RAMB18 / 0 DSP**。
对比之下，最初那版“AXI-Stream + 组合读 FIFO”的写法是 **26,457 LUT**
（79.95%，直接放不下）——差 70 倍，全在“块 RAM 不许组合读”这一条上。

## 3.4 摄像头通路（04_camera）

```
OV5640 DVP ──> 字节配对成 32bit 字 ──> 双时钟行缓冲(pt 写/aclk 读)
            ──> AXI4 突发 ──> DDR ring @0x2000_0000
            ──> dehaze_cam: RGB565 -> BGR888 -> dehaze 核 -> 文件
```

**两个被 testbench 抓出来的真 bug**（都会让板子上电后“看起来能跑但全错”）：

1. **SCCB 的 `S_START → S_BIT` 没有把 `phase` 清 0**。S_BIT 于是多跑了一次 phase3，
   **每个字节少发一个 bit**，寄存器地址和数据整体错位。251 条表写完、ACK 全对、
   波形“看起来正常”，但传感器收到的是垃圾。自检的做法是：把线上每一位解回来
   跟 ROM 内容逐条比对，一跑就现原形。
2. **块 RAM 读少了一拍**。给地址 → 下一拍数据才出来 → 再下一拍才能出示 beat，
   写成三拍时整行数据整体错位一个字。自检按 ring 地址逐字比对，第一行第 1 个字就报错。

**六个被否掉的设计**（留在这里避免下次再走）：

| 方案 | 结果 |
|---|---|
| 手写格雷码异步 FIFO，组合读 `mem[addr]` | 综合展开成 1024×18 mux 树 ≈ 6k LUT，放不下 |
| XPM `xpm_fifo_async` FWFT | 仿真里连续两次读回**同一个字**，每个像素被复制 |
| AXI-Stream + 行缓冲 + 单拍写 | 吞吐 ~1 beat/4 拍，只能靠“FCLK 很慢”才够 |
| 行缓冲整行突发但提前拉 WLAST | AXI 不允许，直接死锁 |
| 3 拍 beat 流水线 | 数据错位一个字 |
| `vs_cnt >= WARMUP` 连续判断 warm-up 门 | 计数在第一帧中途就涨上去，全黑帧漏过 |

**环形缓冲按帧对齐**：1024 行不是 480 的整数倍，若不按帧复位行号，
“读 row 0..479” 只是碰巧对齐。现在采集侧带一个 `line_first`，
写侧看到它就把行号归零，所以**每帧永远从 row 0 开始**。

                  ├─ 49.1 dB ─> HLS C 仿真 ── 逐字节 ─> 板端

三级一致的判据不是 PSNR 而是**逐字节相同**。为此专门写了两个调试工具：

- `check_stageb.py`：用硬件自己的 (a,b) 图在 Python 里复算，一眼区分
  "映射算错"还是"第二级实现错"

## 5. 性能模型与剩余空间

拟合实测数据得到：

```
t ≈ 12.8 × divisor + 124 ms
```

- `12.8 × divisor` 是 PL 的周期开销（随时钟线性缩放）
- **~124 ms 是与时钟无关的地板**，在 div 6 下已占整帧的 62%

**这个地板是什么？两个假设已经被实验证否：**

| 假设 | 实验 | 结果 |
|---|---|---|
| 带宽受限 | 把一帧的 DDR 流量从 28 MB 压到 22 MB（−21%） | **无变化**（226.7 → 226.4 ms） |
| CPU 轮询争用 | `ap_done` 轮询从全速改成每 100 µs 一次 | **无变化**（226.4 → 226.5 ms） |

所以既不是带宽、也不是总线争用。在装上**核内周期计数器**（需要一小段 RTL + 一个可读寄存器）
之前，继续盲改没有意义 —— 必须先看清那 124 ms 落在哪一趟。

**时钟上限**：设计在 divisor 5/6/8 下都逐位正确，在 divisor 4 下出错（v2 时尚能通过，
v3 因 WNS 从 2.703 收紧到 2.683 而失效）。这正好界定了真实 Fmax。

**FCLK0 的换算关系（最终答案）**：

```
FCLK0 = 250 MHz / DIVISOR0        (DIVISOR0 = FPGA0_CLK_CTRL[13:8] @ 0xF8000170)
```

- divisor 20（`0x00201400`）→ 12.5 MHz —— 正是实测那个“~12–14 MHz”
- divisor 8 → 31 MHz，divisor 6 → 42 MHz，divisor 5 → 50 MHz，divisor 4 → 62.5 MHz（出错）
- 独立印证：PS7 配置里 `PCW_ACT_FPGA0_PERIPHERAL_FREQMHZ = 50.000000` 且
  `FCLK0_PERIPHERAL_DIVISOR0 = 5`，250/5 = 50 ✓

所以那条沿用了很久的“精确 50.000 MHz”注释，实际配的是 12.5 MHz。
摄像头通路的 XCLK = FCLK0/4 依赖这个值，因此 `board_run.ps1` 现在显式写
`0x00200500`（50 MHz），并且 `dehaze_cam` 会读核内自由计数器把实测值打出来。

**已尝试但未采纳**：`m_axi` 加宽到 64 bit（2 像素/拍）。考虑到"减少 21% 事务量"完全没有
收益，事务数很可能不是瓶颈，所以没有为此重构数据通路。
